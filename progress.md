  - **V4 is GA and default for new installs since April 2026** — the create-path decision was inverted from "V3 containers only" to "the site's own generation".
  - **V4 detection must key on `widgetType`, not `elType`** — atomic content widgets are still `elType: widget`. Detecting on `elType` would silently corrupt nodes.
  - **V4 typed props nest** — flat `{$$type, value}` assumptions drop content.
  - **Draft-first on published pages means autosave revisions**, a second write path entirely.
  - **Capability-gated `tools/list` is not implementable** under MCP 2026-07-28; resolved by per-site connector URLs, which also binds sessions to one site and fixes the OAuth audience model.
  - **Prompt injection was unaddressed** and is the system's largest risk; §9.1 added.
  - **Nativeness demoted from a build gate to a warning** — as a gate it rewards one large HTML blob over several small ones.

**Worth knowing about walking a raw Elementor element tree in a one-off script:** elements nest (a heading inside a container is not top-level) — a `.find()` over only the top-level `elements` array silently returns `undefined` for anything nested, which reads exactly like "the field doesn't exist" rather than "the search didn't look deep enough." EMCP-040's own first verification run was fooled by this in its own test script (not in the actual write pipeline, which was correct throughout) — write a real recursive helper, even for a quick check.

**Worth knowing before touching `render_preview` or the renderer again:** `renderScreenshot()`/`assertAllowedTarget()` already had `allowedHost`/`selector`/`extraHeaders` support built into their signatures before this session's visible work began (`renderer/src/render.ts`, `renderer/src/egress.ts`) — re-read the actual current source before assuming a capability needs building; the last handoff (written before that renderer-side work was visible in this context) incorrectly implied both gaps were still open in the renderer. Only the `server/`-side pieces (the tool itself, the renderer HTTP client, object storage, `issuePreviewToken`) were actually missing.

**Worth knowing before assuming any WordPress dev sandbox's canonical URL is reachable from a container:** `redirect_canonical()` 301s any request whose Host doesn't match the DB's `siteurl`/`home` option — independent of which URL was requested, so a URL-rewrite alone (matching origin to `WP_BASE_URL`) is not sufficient once WordPress's own redirect fires. Overriding the `Host` header from Playwright/Chromium does not work as a fix — confirmed live, `ERR_INVALID_ARGUMENT`, `Host` is refused even at the CDP layer, not just browser `fetch()`. The real fix here was plugin-side: `Plugin::maybe_skip_canonical_redirect_for_renderer()` cancels `redirect_canonical` when a signature-valid `X-EMCP-Preview-Token` is present (signature-only check, not `redeem()` — a render makes many requests, all carrying the same token, and single-use semantics would fail every request after the first).

**Worth knowing before generating any presigned S3/MinIO URL again:** the URL is signed against the *client instance's own* `endpoint` — a client configured for the docker-internal address (needed for the actual upload) produces a link nothing outside that network can fetch. Use a second client instance, configured with a public-facing endpoint, purely for `getSignedUrl()` — never for actual requests. `server/src/storage/objectStorage.ts`'s `getSigningClient()` is the template.

**Worth knowing before touching the renderer's Docker setup again:** `renderer/package.json`'s `playwright-core` version must exactly match `docker/renderer/Dockerfile`'s base image tag (no caret range) — a mismatch fails `browserType.launch()` outright with Playwright's own clear error message, but only at container runtime, not at `npm install` or `tsc` time, so it's easy to miss until the container actually starts. Chromium needs `--no-sandbox` in this Docker environment or every navigation past loopback silently fails with `ERR_CONNECTION_REFUSED` — a genuinely confusing error since it looks identical to a real network/isolation problem.

**Worth knowing before rendering either WP sandbox, or any Docker-internal target, from inside the renderer again:** the egress filter (EMCP-032) still blocks every render_net target this whole project's local sandboxes live on by default — Docker bridge networks are RFC1918 space, and `wp-v4-pro`/`wp-v3-free`/`minio` all get `ERR_BLOCKED_BY_CLIENT` from any caller that doesn't pass `allowedHost`. This is now resolved for `render_preview` specifically — EMCP-034 wired `allowedHost` through from `WP_BASE_URL`'s own hostname — but any *other* future caller of the renderer (there are none yet) would need to do the same. Don't mistake a blocked render from a different code path for a regression; it's the filter doing its job for anything that hasn't explicitly exempted its one target host.

**Worth knowing before rendering either WP sandbox from inside a container again (a separate, still-open issue):** `wp-v4-pro`/`wp-v3-free`'s `WP_HOME`/`siteurl` are `localhost:<host-mapped-port>`, unreachable from inside any Docker network — a request via the docker-network hostname gets redirected to that unreachable host:port, which shows up as `ERR_CONNECTION_REFUSED` in a browser. Full gotcha in `CLAUDE.md`.

**Worth knowing before touching `wp eval-file` scripts against a live sandbox again:** the `wpcli-*` containers are ephemeral and separate from the actual `wp-v4-pro`/`wp-v3-free` web containers — `error_log()` calls made via `wp eval-file` print to that command's own stdout/stderr (visible directly in the command output) but were **not** observed landing in the web container's `wp-content/debug.log`, even though it's the same shared volume — likely a wp-cli-specific `error_log` ini routing difference, not a defect in the logged code itself (confirmed: the exact same `log()` method's output *did* land in `debug.log` correctly when triggered via a real HTTP request). Don't mistake "not in debug.log" for "didn't log" when the trigger was `wp eval-file`, not a real HTTP request — check the command's own output too.

**Worth knowing before touching `spikes/v4-authoring/` again:** `wp eval-file <script> <args>` (no `--` separator) — positional args land in a `$args` array variable already in scope inside the script, not `$_SERVER['argv']`.

**Worth knowing before restarting the built server against a different sandbox again:** don't reach for `pkill -f 'node dist/index.js'` — in this container, that pattern matches the invoking shell command's own text and kills the wrong thing. Check `/proc/PID/comm` for an exact process-name match, and use `fuser -n tcp <port>` or a live `curl` to confirm something is actually listening — a failed start attempt (`EADDRINUSE`, missing env var) leaves a permanent zombie under this container's `tail -f /dev/null` PID 1, which never reaps children, so `/proc` alone can lie about what's "still running." Also: `docker compose exec` against this container has intermittently reported a spurious timeout/exit-143 on a command that actually succeeded — if that happens, redirect the command's output to a file and read the file back in a separate step rather than assuming the command truly failed.

**Worth knowing before writing a plugin test that needs to prove "never calls X":** type the method parameter as a loose `object` (or an interface, not a concrete Elementor class) so a PHPUnit test can pass a small fake whose forbidden method throws, without needing to stub Elementor's real class hierarchy. `plugin/tests/WidgetsControllerTest.php`'s `ThrowsIfControlsRequestedWidget` (EMCP-027) is the template.

**Worth knowing before stating any new measured budget/threshold in a test:** measure first with a realistic input, *then* set the number — don't pick a round number before running anything. This session got it wrong twice in the same test (EMCP-028's Pro-widget token budget): once by guessing 1,000 before measuring, and once by accidentally testing against an *uncapped* control list (an explicit `limit` override that defeated the very output cap the budget was supposed to prove works). Both were caught by the test actually failing, not assumed correct — but both were avoidable by measuring against the real default path first.

**Worth knowing before touching `label.ts` or any regex involving invisible/zero-width characters again:** don't type the literal character into source at all, even inside a regex character class — build it from `String.fromCharCode()`/numeric code points instead. This session hit real, silent corruption trying to edit a file containing literal zero-width characters (an `Edit` call reported old-string and new-string as byte-identical when they were meant to differ), caught only because the fix was attempted immediately, not because it was anticipated.

**Worth knowing before assuming any widget is introspectable via `get_controls()`:** it isn't, for V4 atomic widgets (`e-`-prefixed) — they use `define_props_schema()` instead, a completely separate mechanism, confirmed against Elementor's own source (EMCP-028). `describe_widget` and `/registry/snapshot` both currently return an empty/near-empty result for these widgets, not an error — don't mistake that for "this widget has no settings."

**Worth knowing before touching `digest.ts` again:** `children` is `DigestChild[]`, a union of `DigestNode | TruncatedNode` — any code walking a digest tree (a new tool, a test, a future compiler/decompiler consumer) needs to check `isTruncatedNode()` before assuming `.kind`/`.native`/`.label`/etc. exist on a given child. `buildDigest()` takes an options object now (`{ maxDepth?, parentGeneration? }`), not a bare second positional argument.

**Worth knowing before editing plugin PHP files again:** they use tabs, not spaces — confirm with `cat -A` before an `Edit` call if a match keeps failing on whitespace that looks identical on screen; this cost real back-and-forth on `RestController.php` this session.
